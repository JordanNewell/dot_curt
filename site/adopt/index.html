Why implement it.

  • Full fidelity — base64 images and tool calls ride in content, verbatim. No flattening, no “best effort”.
  • Unknown fields survive a re-save. Your app's extras aren't a liability.
  • One diffable UTF-8 file per conversation. Archives, version control, and grep all just work.
  • MIT across the board — spec, reference code, schema, fixtures. (Curtis applications themselves are BUSL; the format never is.)

For app developers

Install, round-trip, claim.

The library handles the envelope, the BOM, and the unknown fields. What's left is your integration — and the proof that it holds. 

import { serializeCurt, parseCurt, curtFilename } from 'curt-format';

const body = serializeCurt(conversation, 'my-app@1.0.0');
const back = parseCurt(body);      // CurtConversation | null — null means invalid
const file = curtFilename(back!);  // 2026-10-14 design-review 001.curt

Also in the box: isCurtMessage and isCurtConversation — the spec's validation predicates as type guards — plus the envelope constants CURT_MAGIC and CURT_VERSION. Round-trip a real conversation and confirm unknown fields survive; that is the whole L1 bar.

How to claim conformance

  1. 01
    Run the executable vectors. Everything is plain JSON in conformance/vectors/: core.json (L1, 13 cases), named.json (L2, 7), bulk.json (L3, rules and a canonical example), extensions.json (L4, 6). Twenty-seven checks in all — if your parser accepts what they accept and rejects what they reject, you match the level.
  2. 02
    Update your row in capabilities.json. Set conformanceLevel (e.g. "L1", "L1+L2"), the extensions you emit and accept, and lastAudited. Open a PR — CAPABILITIES.md carries the human-readable audit.
  3. 03
    Link a reproducible run. A CI job or script in your repo that executes the vectors. Claims are self-reported — and reproducible by anyone from the same files.

For tool builders

Schema, fixtures, registry.

  • JSON Schema. Non-normative, for tooling — ships inside the npm package at curt-format/schema/curt-v1.schema.json. Editors, linters, and validators in any language.
  • Round-trip fixtures. tests/fixtures/ — basic.curt, empty.curt, rich.curt, roles.curt — the same files the reference tests run against. Seed your own suite with them.
  • Extension registry. New capability is a PR to EXTENSIONS.md: name, status, the exact fields, any vectors. An entry moves draft → stable when two independent implementations round-trip it.

Questions, answered.

  • Will the spec change under me? No. Core is frozen at v1; evolution is registry-only, and registry entries never change how existing files parse.
  • Who decides? One maintainer, BDFL — deliberately. A format with six committees has no direction.
  • What does draft mean for me? Emit it if you want. Readers must ignore unknown extensions and never reject over them, so nothing breaks.
  • License? MIT — spec, reference code, schema, fixtures. Build a business on it if you like.
NOT YET — STATED PLAINLY

Bindings beyond TypeScript. The predicates are small — Rust, Python, Go, Swift: pick one and keep it in lockstep with SPEC.md. PRs to dot_curt are welcome.

No consumer depends on curt-format yet — five vendored copies and one hand-rolled. Yours can be the first real dependency; the tracker has a row waiting.
